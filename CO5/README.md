## Important evidence boundary

The burst measurements are generated by a deterministic Python transaction-level discrete-event simulator. They are **not** observed production traffic, a MySQL benchmark, or measurements from a physical disk. The 67 requests/second planning rate comes from the assignment scenario. The 20 ms service interval, 32-pool fixture, 16-transaction 2PL admission cap, timestamp jitter and pool starting balances are explicit experiment assumptions used consistently across the generated request sets.

The simulator compares three candidates on the same seed-generated transactions: global serial execution, conservative strict 2PL and commit-atomic strict timestamp ordering. The 81% skew fixture assigns an integer-rounded 81% target of generated requests to the dominant canal pool (exact for 200 and 1,000 requests; whole-request rounding for 10 and 50). The per-farm daily-ceiling check is a separate domain-rule fixture, not silently included in the base token-only performance results; with the test-only ceiling of 25 tokens per farm per day, 773 of 1,000 requests are accepted and 227 are rejected.

## Model limits

1. The simulator models transaction scheduling and validation rather than a complete commercial DBMS buffer manager, network, disk, replication or lock-manager implementation.
2. Conservative strict 2PL acquires its complete known exclusive lock set atomically; therefore, the generated 2PL workload cannot form a partial-lock deadlock. Task 5 separately constructs a dynamic-2PL wait-for cycle and applies deadlock policies to it.
3. Timestamp ordering uses an atomic validation/commit event. A stale attempt is rolled back before publishing any token changes and retried with a larger timestamp. The zero-duration atomic commit step is a simplifying model assumption; do not interpret the TO throughput as a production prediction.
4. Restart times are analytical estimates using the declared log rate and recovery throughput assumptions, not timed crash recovery on a DBMS.
5. The daily farm ceiling is an added domain predicate. The token-only baseline cannot enforce it by itself; the report proposes a farm/day guard row that is checked and updated in the same transaction.
